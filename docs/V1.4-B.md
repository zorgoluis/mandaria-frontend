# Mandaria Web V1.4-B — Repartidores, vehículos y asignaciones

## Alcance y contrato

Implementación en el proyecto existente `mandaria-web` (directorio `mandaria-frontend`). Se inspeccionaron los módulos V1.3, `docs/openapi.json` del backend, OpenAPI servido por `http://localhost:3000/docs-json` (versión 1.4.0), controllers, DTOs, responses, servicios y guards reales antes de desarrollar. No se modificaron el backend ni Coita Eats.

No se añadieron dependencias. Se reutilizan React Router, TanStack Query, Lucide, los formularios HTML y los componentes V1.3. El cambio de versión a 1.4.0 en ambos archivos de paquete identifica la implementación; la validación se informa por separado.

## UI y arquitectura

| Ruta            | Pantalla y comportamiento                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------------- |
| `/drivers`      | Proveedor autorizado, conteos, listado, búsqueda, estado, disponibilidad y paginación                 |
| `/drivers/new`  | Nombre operativo y UUID del User DRIVER existente                                                     |
| `/drivers/:id`  | Usuario, proveedor, estado, disponibilidad persistida, edición de nombre, vehículo actual e historial |
| `/vehicles`     | Proveedor autorizado, conteos, listado, búsqueda, tipo, estado y paginación                           |
| `/vehicles/new` | Identificador, tipo, campos descriptivos opcionales y estado inicial opcional                         |
| `/vehicles/:id` | Información, edición, estado, repartidor actual e historial                                           |

Las rutas conservan el proveedor mediante `?providerId=...`; búsquedas y filtros también son parámetros URL. Es un identificador de selección, nunca una autorización. En detalle de proveedor y Mi proveedor aparecen enlaces con conteos reales a ambos módulos. Se reutiliza exactamente la misma implementación para FLEET e INDEPENDENT.

Carpetas nuevas:

- `src/drivers`: listado, alta, detalle y servicio de repartidores.
- `src/vehicles`: listado, alta, detalle y servicio de vehículos.
- `src/assignments`: selector, desasignación, historial y servicio.
- `src/logistics`: tipos del contrato, selección autorizada de proveedor, conteos, filtros y claves de caché compartidas.

Servicios de dominio → cliente HTTP centralizado. No hay `fetch` dentro de componentes nuevos. Las claves de caché incluyen rol y proveedor; se limpian con el cierre de sesión existente. Las mutaciones invalidan detalles, listados, historial, candidatos y capacidad del proveedor. Los errores se priorizan sobre datos previamente almacenados en caché. Se reutilizan `ActionForm`, `Confirm`, `Modal`, `Table`, `Pagination`, `Badge`, `ErrorState` y notificaciones.

## API consumida

Prefijo común: `/api/v1`.

| Operación                     | SUPER_ADMIN                                         | PROVIDER_ADMIN                                                    |
| ----------------------------- | --------------------------------------------------- | ----------------------------------------------------------------- |
| Seleccionar proveedor         | `GET /admin/providers` y `GET /admin/providers/:id` | `GET /provider/profiles` y `GET /provider/profile?providerId=...` |
| Capacidad                     | `GET /admin/providers/:id/capacity`                 | `GET /provider/capacity?providerId=...`                           |
| Listar / crear repartidores   | `GET/POST /admin/providers/:providerId/drivers`     | `GET/POST /provider/drivers?providerId=...`                       |
| Consultar / editar repartidor | `GET/PATCH .../drivers/:driverId`                   | `GET/PATCH /provider/drivers/:driverId?providerId=...`            |
| Asignar / desasignar          | `POST/DELETE .../drivers/:driverId/vehicle`         | `POST/DELETE /provider/drivers/:driverId/vehicle?providerId=...`  |
| Historial de repartidor       | `GET .../drivers/:driverId/assignments`             | `GET /provider/drivers/:driverId/assignments?providerId=...`      |
| Listar / crear vehículos      | `GET/POST /admin/providers/:providerId/vehicles`    | `GET/POST /provider/vehicles?providerId=...`                      |
| Consultar / editar vehículo   | `GET/PATCH .../vehicles/:vehicleId`                 | `GET/PATCH /provider/vehicles/:vehicleId?providerId=...`          |
| Historial de vehículo         | `GET .../vehicles/:vehicleId/assignments`           | `GET /provider/vehicles/:vehicleId/assignments?providerId=...`    |

En filas con `...`, se conserva `/admin/providers/:providerId`. Los servicios construyen el alcance de manera centralizada y codifican segmentos/parámetros. Los endpoints de auth y los módulos V1.3 se conservan.

### DTOs y respuestas

- `CreateDriverDto`: `{userId, name}`; nombre recortado, 1–100 caracteres; User existente activo de rol DRIVER, sin otro perfil. Nace PENDING/OFFLINE por decisión del backend.
- `UpdateDriverDto`: `{name?, status?}`. Transiciones PENDING→ACTIVE/SUSPENDED, ACTIVE→SUSPENDED, SUSPENDED→ACTIVE. Suspender fuerza OFFLINE, pero conserva la asignación actual.
- `CreateVehicleDto`: `{identifier, type, status?, brand?, model?, year?, color?, plate?}`. Identificador normalizado a mayúsculas, máximo 30 caracteres, único por proveedor. Estado omitido utiliza el default del backend.
- `UpdateVehicleDto`: los mismos campos son opcionales. Los descriptivos aceptan `null` para limpiar. Año entero 1900–2100, marca/modelo máximo 50, color 30, placa 15. Bicicletas sin placa son válidas.
- `AssignVehicleDto`: `{vehicleId}`. Desasignación por DELETE sin body: cierra el registro, no elimina historial.
- Listas e historial: `{items,total,page,pageSize,totalPages}`. Listas de 20; filtros de repartidor `search,status,availability`; vehículo `search,type,status`. El historial no inventa filtros.
- Respuestas incluyen `currentAssignment` o `null`, resúmenes de la contraparte y fechas. User público sin hashes. Capacidad: `{providerId,drivers:{count,max},vehicles:{count,max}}`.

## Roles, seguridad y límites

- Ambos roles administrativos acceden a los módulos; SUPER_ADMIN usa rutas administrativas y selecciona proveedor explícitamente.
- PROVIDER_ADMIN sólo consulta sus memberships. Con exactamente una, la selecciona; con varias, debe elegir. Sin ninguna, muestra estado vacío y no solicita colecciones logísticas. Un providerId ajeno pasa por el guard del backend y recibe 403.
- Cambiar el ID del recurso conservando proveedor propio devuelve 404 seguro, como exige la API. No se muestra información del otro proveedor.
- DRIVER no tiene acceso a las rutas logísticas ni nuevos menús administrativos. No se implementó una aplicación de repartidor.
- Availability sólo se muestra; no se consume `/driver/availability` desde el panel.
- La capacidad incluye todos los estados. Se utiliza `/capacity`; los filtros de una tabla no alteran el conteo. El alta se deshabilita al alcanzar el límite, incluso al abrir `/new` manualmente. Los conflictos 409 siguen siendo autoridad del backend.
- Selector de asignación: consulta vehículos ACTIVE del mismo proveedor por páginas, excluye ocupados y permite buscar. La paginación indica el total de vehículos activos, porque no existe filtro `unassigned` del servidor. Puede haber una página sin vehículos libres y otras con candidatos.
- Confirmaciones para cambios de estado y desasignación. Se muestran mensajes españoles conocidos para límite, duplicados, ocupado, suspensión, mantenimiento y recurso no disponible. Errores 400/401/403/404/409/429/500/red mantienen la normalización segura.
- Auth sin cambios: access token en memoria, refresh token en sessionStorage, rotación coordinada y expiración/cierre existentes. No se persisten passwords, clientSecrets ni credenciales B2B. Ninguna variable Vite nueva.

## Dashboard y capacidades que no existen

El dashboard de PROVIDER_ADMIN incorpora capacidad real y dos consultas `pageSize=1` para los totales de repartidores activos/disponibles y vehículos activos del proveedor seleccionado. No descarga colecciones para contar. La disponibilidad es persistida, no seguimiento en vivo.

Se omiten totales logísticos **globales** del dashboard SUPER_ADMIN: no existe un endpoint de agregado global. Tampoco existen listado global de repartidores/vehículos, selector de Users autorizado para PROVIDER_ADMIN, creación administrativa de User, filtro servidor de vehículos libres ni eliminación de recursos logísticos. Se documentan estas limitaciones en lugar de inventar contratos; por ello el alta de repartidor solicita el UUID previamente aprovisionado.

## Hallazgos y deuda técnica

- Se corrigió la accesibilidad de `Field`: `aria-labelledby` referencia sólo la etiqueta y `aria-describedby` la ayuda. Chromium antes incluía textos de las opciones en el nombre accesible del selector.
- Se corrigió la invalidación de consultas al editar límites/estado de Provider para actualizar también la capacidad logística; incluye regresión automatizada.
- Durante el desarrollo, la prueba rápida provocó un 429 real en refresh; se validó el mensaje seguro y se ajustó el ritmo del script, sin alterar rate limiting.
- Se conserva la advertencia de cambios al cerrar/recargar de V1.3; todavía no hay confirmación de descarte en navegación interna.
- No hay websockets, mapas, pedidos, dispatch, entregas, pagos, wallets, documentos ni funcionalidades V1.5.
- CI sigue pendiente por instrucción del usuario. No se ejecuta Docker en esta tarea. No se realiza commit ni push.
