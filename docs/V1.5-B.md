# Mandaria Web V1.5-B — Administración de Delivery Requests

## Alcance y contrato

Fuente: Mandaria Backend V1.5.0 (`docs/openapi.json`, `admin-delivery-requests.controller.ts`, `delivery-requests.dto.ts`, `delivery-requests.responses.ts`, `delivery-request.select.ts`, `delivery-requests.service.ts` y `prisma/schema.prisma`), inspeccionados el 2026-09-15. No se modificó backend ni Coita Eats.

Mandaria Web V1.5 permite observar **qué se solicitó transportar** y cancelar solicitudes `CREATED`. No administra costos, cotizaciones ni quién realizará la entrega (V1.6/V1.7).

## API consumida

Todos con prefijo `/api/v1`, Bearer humano, `@Roles('SUPER_ADMIN')`. PROVIDER_ADMIN y DRIVER reciben 403.

| Método y ruta                                  | Uso                                                                                                                                                                              |
| ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| GET /admin/delivery-requests                   | `page`, `pageSize` (1–100), `publicId` (`MDR-\d{6,}`), `integrationClientId` (uuid), `externalReference` (exacto, ≤100), `status`, `requestedFrom`/`requestedTo` (ISO date-time) |
| GET /admin/delivery-requests/:publicId         | Detalle con stops, packages, financialContext e integrationClient                                                                                                                |
| POST /admin/delivery-requests/:publicId/cancel | `{reason}` 1–500. CREATED → CANCELLED. Repetir sobre CANCELLED responde 200 conservando motivo y fecha originales                                                                |
| GET /admin/integrations                        | Opciones del filtro por integración (hasta 100, contrato V1.3)                                                                                                                   |

Respuestas: `goodsValue` es string con 2 decimales (se formatea, nunca se recalcula); medidas y coordenadas son números; `financialContext` es relación opcional en el esquema y la UI tolera `null`. El listado resume **sin stops**: no incluye dirección ni contacto, por lo que la lista no muestra resumen de recogida/entrega (no se hacen N consultas de detalle). Orden `requestedAt DESC`.

El contrato admin no declara 409. Los errores 400/401/403/404/409/429/500/red pasan por `normalizeError`; sólo se traducen mensajes conocidos (`Delivery request not found`, rango de fechas).

## UI y arquitectura

| Ruta                         | Pantalla                                                                                                |
| ---------------------------- | ------------------------------------------------------------------------------------------------------- |
| /delivery-requests           | `DeliveryRequestsPage`: filtros servidor en URL, tabla apilable en móvil, paginación, estado vacío      |
| /delivery-requests/:publicId | `DeliveryRequestDetail`: resumen, cancelación, recogida, entrega, paquetes, contexto económico, técnica |

- `src/delivery-requests/types.ts`: tipos del contrato (no hay generador OpenAPI en el proyecto).
- `service.ts`: única capa HTTP, sobre `api()` existente. `queries.ts`: claves React Query.
- `format.ts`: etiquetas de categoría y modalidad, peso, dimensiones (`No informadas`, nunca `null`), moneda y límites de día para fechas.
- `pages.tsx`: páginas y `CancelDialog` (modal + `ActionForm` con motivo obligatorio).
- Compartidos: `Table` acepta `stacked` (tarjetas etiquetadas bajo 850px); `ActionForm` acepta `cancelLabel`. Ambos opcionales y compatibles con V1.4.
- Sidebar: `Solicitudes` después de `Vehículos`, sólo SUPER_ADMIN. Rutas dentro de `Protected roles={['SUPER_ADMIN']}`: el acceso manual muestra 403 sin llamar a la API.
- Dashboard SUPER_ADMIN: `Solicitudes creadas` y `Solicitudes canceladas` con `pageSize=1` + `status`; el backend calcula `count` con índice `(status, requestedAt)`.
- Integración: el detalle enlaza a `/integrations/:id`; el detalle de integración enlaza a `/delivery-requests?integrationClientId=…`.
- `publicId` es el título; UUIDs sólo en información técnica. `externalReference` nula se muestra `—`.
- Sin botones de edición ni eliminación. Sin mapa, distancia, cotización ni costo de envío.

Fechas: `Desde`/`Hasta` son días locales convertidos a `00:00:00.000` y `23:59:59.999` locales en ISO. Filtros inválidos en la URL (publicId, uuid, estado, rango) muestran error y no llaman al backend.

## Datos personales

Nombres, teléfonos y direcciones sólo viven en la caché en memoria de React Query (se limpia en logout/expiración). No se escriben en consola, `localStorage`, `sessionStorage` ni URL. No existe telemetría frontend. Las pruebas unitarias y de navegador lo verifican.

## Pruebas y reproducción

- `src/test/delivery-requests.test.tsx`: menú, lista, vacío, filtros/paginación servidor, filtros inválidos, errores, detalle A/B/C, múltiples paquetes, PREPAID, COURIER_ADVANCE, cancelada, referencia nula, cancelación (confirmación, motivo, éxito, error, doble cancelación), PROVIDER_ADMIN/DRIVER bloqueados, dashboard y datos personales.
- `src/test/delivery-requests-api.test.ts`: rutas/payloads reales, errores seguros y formateo.
- `src/test/flows.test.tsx`: navegación exacta SUPER_ADMIN y 403 de PROVIDER_ADMIN en rutas nuevas.
- `npm run test:e2e:delivery-requests` (`scripts/verify-delivery-requests.mjs`): navegador real contra backend local.

```bash
MANDARIA_BACKEND_ENV=../mandaria-backend/.env E2E_MDR_CANCEL=MDR-000008 npm run test:e2e:delivery-requests
```

Variables: `E2E_MDR_CANCEL` (obligatoria, única solicitud que se cancela), `E2E_MDR_A/B/C` (opcionales; si faltan se eligen por criterio), `E2E_BROWSER_CHANNEL` (p. ej. `msedge` si no están instalados los navegadores de Playwright). Las solicitudes se crean con la API B2B real de V1.5 (Idempotency-Key, credencial temporal revocada al terminar).

## Hallazgos

1. **Bug corregido (filtros):** React Router aplica `setSearchParams` en una transición. El formulario resincronizaba su borrador con la URL todavía anterior: tras `Limpiar`, un estado seleccionado de inmediato reenviaba el `publicId` previo, y fechas escritas justo después podían borrarse. Ahora sólo los cambios de URL que el formulario no aplicó (atrás/adelante, enlaces) reemplazan el borrador. Detectado y verificado con la prueba de navegador real (dos corridas 11/11 consecutivas); jsdom no reproduce ese orden, la prueba unitaria sólo cubre el flujo funcional.
2. El listado admin no incluye stops; resumen de recogida/entrega sólo en detalle.
3. El detalle no expone quién canceló (el actor sólo va al log del backend).
