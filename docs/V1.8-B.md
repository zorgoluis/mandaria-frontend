# Mandaria Web V1.8-B — Asignación de repartidor y vehículo

## Alcance y contrato

Fuente: Mandaria Backend V1.8.0, inspeccionado el 2026-09-18. La rama `QA` y `origin/v1.8-provider_driver_vehicle_assignment` son idénticas en todos los archivos consumidos (`git diff` vacío), y ambas publican OpenAPI 1.8.0 con las mismas rutas (`docs/openapi.json`, `delivery-assignments.dto.ts`, `delivery-assignments.responses.ts`, `delivery-assignments.service.ts`, `provider-assignments.controller.ts`, `admin-assignments.controller.ts`, `assignment-policy.ts` y `dispatch/dispatch.select.ts`). No se modificó backend ni Coita Eats.

V1.8 responde **quién ejecuta un servicio ya tomado**. El Dispatch sigue siendo `CLAIMED`: no se agregó `ASSIGNED` a `DispatchStatus`; que esté asignado se deriva de la `DeliveryAssignment` real.

### Discrepancias verificadas contra el código real

1. **`assignmentDeadline`, `assignmentOverdue` y `assignment` no aparecen en `docs/openapi.json`**, pero el backend sí los devuelve: `providerDispatchView` los inyecta en la respuesta (`assignment` sólo para el dueño del claim). El Swagger de esa rama está desactualizado respecto a su propio código; se consumen los campos reales.
2. En la vista de proveedor el campo es **`assignment`**; `activeAssignment` existe sólo en la vista de auditoría de SUPER_ADMIN.
3. `GET /provider/dispatches/{id}/assignments` devuelve un **arreglo**, no una página.

## API consumida

Prefijo `/api/v1`, JWT humano. Las operaciones son de `PROVIDER_ADMIN` con membership vigente y claim del Dispatch; `providerId` en query sólo elige entre mis memberships y **nunca viaja en el body**: el backend deriva el proveedor del membership y del Dispatch.

| Método y ruta                                      | Uso                                                                                                    |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| POST /provider/dispatches/{id}/assignment          | `{driverId,vehicleId}` → 201 con `paymentContext`. Bloqueos Dispatch → proveedor → Driver → Vehicle    |
| POST /provider/dispatches/{id}/assignment/reassign | `{driverId,vehicleId,reason,reasonDetail?}` → 200. La ACTIVE pasa a REASSIGNED en la misma transacción |
| POST /provider/dispatches/{id}/assignment/cancel   | `{reason,reasonDetail?}` → 200. La ACTIVE pasa a CANCELLED y libera Driver y Vehicle                   |
| GET /provider/dispatches/{id}/assignments          | Arreglo, de la más reciente a la más antigua. Nunca incluye asignaciones de otros proveedores          |
| GET /provider/dispatches/{id}/available-drivers    | Drivers ACTIVE de mi proveedor, con cuenta activa y sin asignación de entrega ACTIVE. Paginado         |
| GET /provider/dispatches/{id}/available-vehicles   | Vehicles ACTIVE de mi proveedor sin asignación de entrega ACTIVE. Paginado                             |
| GET /admin/dispatches/{id}/assignments             | Sólo SUPER_ADMIN, lectura y auditoría. Incluye el proveedor de cada asignación                         |

`reason` admite `DRIVER_UNAVAILABLE`, `VEHICLE_ISSUE`, `OPERATIONAL_CHANGE` y `OTHER`; `DELIVERY_CANCELLED` está reservado a la cancelación oficial del servicio y la web nunca lo envía. `reasonDetail` es obligatorio con `OTHER` (3–500 caracteres).

### Dos contratos monetarios

El CHECK del backend lo confirma y el frontend lo respeta sin adivinar:

- `paymentContext.*` (endpoints de asignación) usa **`MoneyResponse`**: `{amount, currency}`.
- `service.goods` (Dispatch, V1.7) conserva **decimal como string con `currency` como campo hermano**.

`paymentFromService()` en `src/delivery-assignments/format.ts` normaliza ambos a una sola forma, de modo que ningún componente adivina el contrato. El costo del envío y el valor de la mercancía **nunca se suman**: V1.8 no define un total operacional.

## Regla de concurrencia

El backend es la única autoridad del Assignment activo. El CHECK V1.8-A demostró que dos reasignaciones concurrentes se serializan y **ambas responden 200**, así que un 200 no prueba que lo que envió este navegador siga siendo lo ACTIVE.

`refreshAfterAssignment()` (`src/delivery-assignments/queries.ts`) se ejecuta tras cada `assign`, `reassign` y `cancel`: invalida el árbol de Dispatches del proveedor y las tres consultas de asignación, y **espera** el refetch del detalle y del historial antes de cerrar el diálogo. La respuesta de la mutación no se usa como estado: el panel renderiza lo que devuelve `GET /assignments`, donde el ACTIVE se busca por `status`. La prueba `renders the winner of a concurrent reassignment` fija esta regla: la mutación responde Pedro y el refetch dice Luis, y la UI muestra a Luis.

## UI y arquitectura

| Ruta            | Qué agrega V1.8                                                                             |
| --------------- | ------------------------------------------------------------------------------------------- |
| /services       | Cada servicio tomado muestra `Pendiente de asignación` o `Asignado · repartidor · vehículo` |
| /services/:id   | Panel `Asignación`: activo, historial, ASIGNAR / REASIGNAR / CANCELAR ASIGNACIÓN            |
| /dispatches/:id | Sección `Asignaciones` de sólo lectura para SUPER_ADMIN                                     |

- `src/delivery-assignments/`: `types.ts`, `service.ts` (única capa HTTP), `queries.ts` (claves y refetch), `format.ts` (etiquetas, dinero, cuenta regresiva), `use-assignments.ts` (hook), `components.tsx` (diálogos, contexto de pago, historial) y `panel.tsx`.
- No se recalcula elegibilidad: los candidatos salen de `available-drivers` y `available-vehicles`. La única regla local replica el emparejamiento V1.4 que el backend ya envió (`pairedVehicle` / `pairedDriver`), para que el operador no arme una combinación que el backend rechazaría con `DRIVER_VEHICLE_MISMATCH`.
- Sin presencia en tiempo real: `availability` se muestra como `Sin servicio en curso` / `Marcado como ocupado` / `Sin conexión reciente`, nunca como «en línea».
- **Protección de liberación**: con una asignación ACTIVE, `LIBERAR SERVICIO` queda deshabilitado en la tarjeta y en el detalle, con la indicación de cancelar primero. El backend también lo protege con `DISPATCH_HAS_ACTIVE_ASSIGNMENT`.
- **Deadline**: se usan `assignmentDeadline` y `assignmentOverdue` del backend. No hay cron ni liberación automática; sin repartidores o vehículos disponibles se muestra un estado vacío y la decisión queda en el operador.
- Los 12 códigos 409 (`DRIVER_BUSY`, `VEHICLE_BUSY`, `DRIVER_VEHICLE_MISMATCH`, `DRIVER_NOT_ELIGIBLE`, `VEHICLE_NOT_ELIGIBLE`, `DISPATCH_ALREADY_ASSIGNED`, `DISPATCH_HAS_ACTIVE_ASSIGNMENT`, `NO_ACTIVE_ASSIGNMENT`, `ASSIGNMENT_UNCHANGED`, `ASSIGNMENT_CONFLICT`, `PROVIDER_NOT_ACTIVE`, `DISPATCH_NOT_CLAIMED_BY_PROVIDER`) se traducen en `services/errors.ts`; el texto crudo del backend nunca llega a pantalla.

## Roles

`PROVIDER_ADMIN` dueño del claim opera; un `PROVIDER_ADMIN` ajeno recibe el 403 real del backend y la UI no llama a ningún endpoint de asignación; `DRIVER` no accede a la central; `SUPER_ADMIN` sólo lee el historial y no ve ASIGNAR, REASIGNAR ni CANCELAR ASIGNACIÓN.

## Validación en navegador: CHECK final V1.8

`npm run test:e2e:assignment` (`scripts/verify-assignment.mjs`) ejecuta el CHECK final contra backend y navegador reales: **17 comprobaciones, dos corridas consecutivas en verde** con escenario fresco sembrado entre ellas. El script se niega a correr si el proveedor de rutas no es `local_fake`, de modo que nunca gasta en Google Routes.

```bash
MANDARIA_BACKEND_ENV=../mandaria-backend/.env npm run test:e2e:assignment
```

Cubre los doce escenarios del CHECK: flujo principal desde la web, mercancía prepagada, adelanto en efectivo, repartidor ocupado, vehículo ocupado, reasignación con historial, protección de liberación, aislamiento de proveedor, concurrencia, cancelación oficial, historial completo y deadline de asignación; más visibilidad por rol, responsive a 390 px y auditoría de secretos.

Lo deducido del código y no del Swagger quedó **confirmado en vivo**: `GET /provider/dispatches/:id` devuelve `assignment`, `assignmentDeadline` y `assignmentOverdue`, y `assignmentDeadline` es distinto de `expiresAt`.

La concurrencia se comportó como documenta el CHECK V1.8-A: dos reasignaciones simultáneas respondieron **`200, 200`** y el backend dejó exactamente una asignación ACTIVE por despacho, por repartidor y por vehículo.

### Precondiciones del entorno

Tres requisitos que no son de V1.8 pero sin los cuales no hay nada que asignar:

1. El proveedor necesita una **`ProviderServiceCoverage` ACTIVA** para la zona y el tipo de servicio; sin ella el Dispatch se abre con cero candidatos (`noProviderAvailable: true`) y los candidatos se congelan al abrirlo. Mandaria Web no administra la cobertura: es funcionalidad V1.7 sin interfaz.
2. Los **Drivers nacen `PENDING`** y `available-drivers` sólo lista los `ACTIVE`; hay que activarlos con `PATCH /admin/providers/:id/drivers/:driverId`.
3. El backend debe correr con `ROUTING_PROVIDER=local_fake` para no llamar a la API de pago al cotizar.
