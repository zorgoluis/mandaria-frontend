# Mandaria Web V1.9-C — Administración de cobertura de servicio

## Alcance y contrato

Fuente: Mandaria Backend 1.9.0 (rama `v1.9-independent_drivers`): `dispatch/admin-dispatches.controller.ts`, `provider-dispatches.controller.ts`, `provider-coverages.service.ts`, `dispatch.dto.ts` y `dispatch.responses.ts`, contrastados con el servidor real el 2026-09-21. Sin cambios de backend, dominio ni migraciones; sin endpoints nuevos.

V1.9-C elimina la dependencia de scripts o llamadas manuales a la API para decidir qué proveedores reciben servicios. La cobertura (`ProviderServiceCoverage`) es la combinación única **proveedor + zona + tipo de servicio**, en estado `ACTIVE` o `INACTIVE`, y la **administra Mandaria**, no el proveedor.

### Autorización verificada en código y en vivo

| Ruta                                                     | Guardas reales                                                                     | Resultado en vivo                           |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------- |
| GET/POST /admin/providers/:providerId/service-coverages  | `AccessGuard`, `RolesGuard`, `@Roles('SUPER_ADMIN')`                               | PROVIDER_ADMIN 403, DRIVER 403, B2B 401/403 |
| PATCH /admin/providers/:providerId/service-coverages/:id | Igual                                                                              | PROVIDER_ADMIN 403                          |
| GET /provider/service-coverages?providerId=              | `AccessGuard`, `RolesGuard`, `ProviderMembershipGuard`, `@Roles('PROVIDER_ADMIN')` | Otro proveedor rechazado; DRIVER 403        |
| POST/PATCH /provider/service-coverages, DELETE en admin  | No existen                                                                         | 404                                         |

### Asimetría del contrato

- **Escritura (POST):** `{serviceZoneId, serviceType}`, plano.
- **Lectura (GET y respuestas de POST/PATCH):** `{id, providerId, serviceType, status, createdAt, updatedAt, serviceZone: {id, code, name, status}}`. **No existe `serviceZoneId`** en la respuesta; los tipos de la web representan exactamente eso.
- **PATCH:** `{status: ACTIVE | INACTIVE}`, idempotente. **No hay DELETE**: una cobertura se desactiva, nunca se borra.
- **409 `SERVICE_COVERAGE_EXISTS`** no trae el id de la fila existente. La web la localiza en la lista recién refrescada.
- El alta **no restringe zonas inactivas**. La web las ofrece marcadas «(inactiva)» y avisa de que una zona inactiva no recibe servicios nuevos.

## Qué afecta la cobertura

- La cobertura decide los **candidatos Provider de los Dispatches que se abran a partir de ese momento**.
- **Los candidatos de los Dispatches ya abiertos no se recalculan**: activar una cobertura no añade al proveedor a servicios ya abiertos.
- Desactivarla no lo retira de la lista de candidatos de un servicio ya abierto, pero **el backend revalida al reclamar**: el proveedor recibe `PROVIDER_NOT_ELIGIBLE` y ya no puede tomarlo. El aviso de la web lo dice.
- Sin cobertura activa el Dispatch **sí se abre** (`OPEN`, `candidates: []`, `noProviderAvailable: true`); `noProviderAvailable` es un campo derivado, no un estado: no existe `NO_PROVIDER`. La web nunca dice que «no se crearán servicios».
- Los repartidores independientes no usan cobertura: su elegibilidad es la política V1.9. V1.9-C no añade cobertura a independientes.

## UI

| Dónde                                            | Rol            | Qué hace                                                                  |
| ------------------------------------------------ | -------------- | ------------------------------------------------------------------------- |
| /providers/:id → sección «Cobertura de servicio» | SUPER_ADMIN    | Lista zona, tipo y estado; agregar; activar y desactivar con confirmación |
| /provider/profile → sección «Mi cobertura»       | PROVIDER_ADMIN | Sólo lectura de la cobertura propia, sin ningún control                   |

- **Módulo:** `src/service-coverage/` (`types`, `service`, `queries`, `format`, `pages`). Reutiliza el catálogo de zonas (`serviceZones.list`) y de tipos de servicio (`serviceTypes`, `serviceTypeLabels`) de V1.6; no duplica catálogos.
- **Tipos de servicio:** se ofrecen desde el enum real (hoy sólo `LOCAL_DELIVERY` → «Entrega local»). Un valor nuevo del backend se muestra como «Otro tipo de servicio» hasta tener su etiqueta, sin reconstruir la pantalla.
- **Reactivación:** si el alta choca con una fila `INACTIVE`, el diálogo dice «Esta cobertura ya existe, pero está desactivada. ¿Deseas reactivarla?» con **Cancelar** y **Reactivar**, y reactiva con PATCH sobre esa fila. Si la fila ya está activa, lo dice y no hace nada.
- **Estado real:** tras cada POST o PATCH se espera el refetch del backend antes de cerrar el diálogo; nunca estado optimista.
- **Accesibilidad:** las acciones de fila son objetivos de 44 px en pantallas de hasta 850 px, la tabla se apila en móvil y los estados de carga, vacío y error son explícitos.
- **Indicador opcional por zona («proveedores con cobertura activa»):** no implementado. Sin un endpoint por zona exigiría consultar la cobertura de cada proveedor (N+1). Queda como mejora futura de backend.

## Validación real (2026-09-21)

Backend real con `ROUTING_PROVIDER=local_fake` y navegador real (Playwright), sobre Rápidos de Coita:

- **A. Crear** Tuxtla + Entrega local desde la web: persiste `ACTIVE` y la lectura trae `serviceZone` anidada.
- **B. Desactivar:** `INACTIVE` en backend.
- **C. Volver a crear:** 409 reconocido y reactivación ofrecida, sin duplicado.
- **D. Reactivar:** PATCH sobre la misma fila, `ACTIVE`.
- **Regresión de Dispatch desde la web:**
  - D1 con Ocozocoautla activa incluye a Rápidos.
  - Tras desactivarla, D1 conserva sus candidatos, pero el claim de Rápidos recibe `PROVIDER_NOT_ELIGIBLE`.
  - D2 nuevo ya no lo incluye.
  - Tras reactivarla, D3 lo vuelve a incluir, y D2 no se recalcula.
- **Proveedor:** `/provider/service-coverages` refleja exactamente los cambios del SUPER_ADMIN; toda mutación directa se rechaza.
- **Responsive:** 375, 768 y escritorio sin desbordamiento horizontal.

Al terminar se restauró el estado: Ocozocoautla `ACTIVE`; la fila de Tuxtla de Rápidos queda `INACTIVE` como fixture identificado, porque no existe DELETE.
