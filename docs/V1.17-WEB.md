### Procedimiento operativo actual

1. Tras respuesta perdida no repetir una intención. Marcador durable: actor, operación (kind), clave y referencias; aceptar conserva MDR+MQ para validar identidad. Marcadores anteriores siguen siendo legibles. Nuevas políticas no persisten pagador/revisión esperada. Sin cuerpos, contactos, tokens o consentimientos persistidos.
2. Iniciar sesión como actor original y **Consultar resultado**. Otra cuenta conserva bloqueo sin botones de consulta/cierre. No borrar storage ni fabricar claves. GET/cierre no requieren cuerpo original.
3. **APPLIED**: validar operación/recurso/recibo; leer MPQ actual o MDR/status/consent-context, o política actual; refrescar consultas antes de retirar marcador. Recibo antiguo nunca reemplaza una política posterior ni reabre solicitud terminal. Error o incoherencia conserva bloqueo.
4. **PENDING_OR_UNKNOWN**: mantener marcador. Consultar otra vez o confirmar explícitamente **Cerrar intento técnico**. Cerrar impide publicación del recurso/confirmación de política; no cancela servicios ni revierte entregas físicas, routing o presupuesto autorizado. NONE_STARTED de GET pendiente no garantiza ausencia futura de efectos.
5. Timeout de cierre: conservar bloqueo y consultar GET, incluso tras recarga. No asumir CLOSED_NO_EFFECTS ni repetir automáticamente.
6. **CLOSED_NO_EFFECTS** se limita a recurso/política: no significa que no ocurrió absolutamente nada. Sólo canPrepareNewAttempt=true ofrece **Preparar otra intención** con confirmación desmarcada. Vuelve a consultar cierre y refresca vistas antes de retirar marcador. No envía comandos.
7. 409 **COMMAND_ATTEMPT_CLOSED** conserva marcador y solicita consulta. COMMAND_ATTEMPT_SCOPE_CONFLICT requiere revisar clave/referencia sin sustituirlas. Ningún estado desconocido permite otra intención.
8. Otro dispositivo: entrar a MDR propia desde historial/solicitud activa. consent-context recupera MQ y términos finales sin storage anterior. Revisar y consentir explícitamente; no aceptación automática ni extensión de TTL.
9. Cancelación/perfil conservan contratos anteriores: no se inventa operación CANCEL en HumanAttemptResult. Marcador legado de aceptación sin MQ suficiente falla cerrado y requiere soporte.

Persistencia local no garantiza bloqueo global entre dispositivos o ante borrado deliberado. Backend mantiene autoridad sobre propiedad, cupo e idempotencia. Recibo recuperado sólo temporal, nunca sustituto del estado vigente.

## Recuperación y procedimiento operativo

1. Durante una operación se conserva el cuerpo JSON original sólo en memoria; storage contiene actor, tipo, clave, referencia pública y referencia relacionada (MQ o pagador/revisión de política), sin contactos/contraseñas/tokens.
2. En respuesta perdida, 5xx, sesión perdida o conflicto no concluyente: mostrar «Pendiente de reconciliación», sin otra intención. Recuperación explícita en la misma sesión puede enviar exactamente la misma clave/cuerpo. Un error de permiso al recuperar NO elimina la incertidumbre original.
3. Tras recargar, el cuerpo ya no existe. Consulta MPQ para una conversión: sólo CONVERTED con referencia MDR coherente permite continuar. Consulta status para aceptación: requiere la MQ aceptada esperada con importe; para cancelación, CANCELLED confirmado. Vencimiento o ausencia de efectos no prueba cierre del POST tardío.
4. Otra cuenta no recupera el intento del actor inicial. Los marcadores siguen bloqueando tras logout/cambio de usuario. No borrar almacenamiento para sortearlos. Al cerrar sesión se eliminan cuerpos en memoria.
5. Las referencias MPQ↔MDR propias se guardan por actor para volver desde el historial al consentimiento, sin contactos ni cuerpos. En otro dispositivo pueden no estar disponibles; no se fabrica consentimiento.
6. Política: tras respuesta perdida consultar. Si pagador y revisión coinciden con el cambio solicitado, queda confirmada la configuración deseada; si no, conservar bloqueo. Replay explícito sólo con cuerpo original en memoria. Nunca POST automático.
7. Cambios de tipo/perfil perdidos obligan a consultar GET perfil/revisión antes de volver a modificar; al recargar se obtiene nuevamente el perfil. No se reutiliza una revisión nueva automáticamente.

Persistencia local no constituye una garantía global entre dispositivos ni sobrevive a borrado deliberado del almacenamiento; backend conserva autoridad sobre cupo/ownership/idempotencia. Storage inaccesible/corrupto falla cerrado mediante límite de error de aplicación, sin enviar POST.

## Brechas exactas y divergencias para BACKEND

- Creación MPQ con respuesta perdida seguida de recarga: no hay en las rutas vigentes una consulta autorizada de creación por Idempotency-Key ni listado de MPQ propias que recupere la referencia. Sin cuerpo original no se puede reproducir con seguridad. Se conserva bloqueo. Backend necesitaría recibo consultable por actor/clave (y cierre seguro si se pretende acreditar ausencia de efectos); no se inventó ruta.
- Una conversión todavía no observada, aceptación no observada o política no coincidente tampoco prueban que un POST tardío no se aplicará. Sin recibo/cierre de estas intenciones tras perder el cuerpo, el estado sigue incierto y requiere soporte. No se utilizan los endpoints de intentos DRIVER/custodia para estas operaciones distintas.
- La MDR humana no expone referencia MPQ ni una ruta propia para recuperar MQ por MDR. Sin la referencia local o la URL original no se puede preparar consentimiento después de cambiar de dispositivo. No se toma el hash MPQ como sustituto del hash MDR.
- Corrección del diagnóstico inicial: OFFER ya era parte del contrato backend. No se acredita una omisión ni un cambio funcional nuevo; se conserva su presentación informativa.
- OpenAPI administrativo declara IntegrationClient no nullable; Prisma XOR y `delivery-request.select.ts`/toSummary/toDetail conservan null para solicitudes directas. Frontend adapta ese null como «Cliente directo». Backend debería ajustar sus esquemas documentales.

## Seguridad de acceso

El fragmento token/purpose se consume antes de restaurar la sesión y se elimina de la barra. Sólo queda en memoria de la pantalla; salir/recargar lo retira. VERIFY exige login de la cuenta receptora, confirmado por backend. 202 sólo reconoce una solicitud, no entrega de correo. Reset 200 requiere login nuevo. No se registran valores de tokens, contraseñas o contactos en logs/capturas reales.
