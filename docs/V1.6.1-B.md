# Mandaria Web V1.6.1-B — Invitaciones y activación de cuentas

## Alcance

**Production user provisioning no longer requires local seeds.** Mandaria Web incorpora administradores de proveedor y repartidores reales mediante invitación por correo y activación con contraseña elegida por la persona invitada. Los seeds (`db:seed:local-provider-admins`, `db:seed:local-driver-users`) siguen siendo sólo herramientas de desarrollo y validación local.

Fuente del contrato: Mandaria Backend V1.6.1 (`docs/openapi.json` 1.6.1, `src/invitations/*`, `src/users/*`, `src/common/password-policy.ts`, `src/common/http-exception.filter.ts`, `src/auth/auth.service.ts`), inspeccionado el 2026-09-16. No se modificó backend ni Coita Eats. No se implementó Dispatch V1.7, recuperación de contraseña, MFA, registro público ni login social.

## API consumida

| Método y ruta                                                       | Uso en la web                                                                                                                 |
| ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| POST /admin/providers/:providerId/invitations                       | SUPER_ADMIN. PROVIDER_ADMIN: `{email, role: 'PROVIDER_ADMIN', membershipRole}`; DRIVER: `{email, role: 'DRIVER', driverName}` |
| GET /admin/user-invitations                                         | SUPER_ADMIN. `page, pageSize, status, role, providerId, search`                                                               |
| POST /admin/user-invitations/:id/resend · /revoke                   | SUPER_ADMIN. Sin body                                                                                                         |
| POST /provider/driver-invitations?providerId=                       | PROVIDER_ADMIN. `{email, driverName}`: el body no lleva `role` ni `providerId`                                                |
| GET /provider/driver-invitations?providerId=                        | PROVIDER_ADMIN. `page, pageSize, status, search`                                                                              |
| POST /provider/driver-invitations/:id/resend · /revoke ?providerId= | PROVIDER_ADMIN. Sin body                                                                                                      |
| POST /auth/activate-account                                         | Pública. `{token, password}` → `{status: 'ACTIVE', email, role}`; no devuelve sesión                                          |
| GET /users?status=                                                  | SUPER_ADMIN. Cada usuario trae `status: INVITED \| ACTIVE \| DISABLED`                                                        |

No se usa `GET .../invitations/:id` (el listado ya trae todo lo necesario). El rol global se fija en el código de cada flujo, nunca desde datos de formulario; SUPER_ADMIN no es invitable en el backend. `membershipRole` (Propietario/Administrador) es obligatorio para PROVIDER_ADMIN según el DTO.

## Rutas y pantallas

| Ruta                | Acceso                      | Contenido                                                                                                |
| ------------------- | --------------------------- | -------------------------------------------------------------------------------------------------------- |
| `/users`            | SUPER_ADMIN                 | Estado real de cuenta, filtro servidor por estado, **[Invitar administrador]** con selector de proveedor |
| `/invitations`      | SUPER_ADMIN (nuevo)         | Todas las invitaciones: filtros estado/rol/correo, reenviar, revocar                                     |
| `/providers/:id`    | SUPER_ADMIN                 | Panel **Administradores** con [Invitar administrador] (proveedor fijo) e **Invitaciones del proveedor**  |
| `/drivers`          | SUPER_ADMIN, PROVIDER_ADMIN | **[Invitar repartidor]** e **Invitaciones de repartidores** del proveedor en contexto                    |
| `/activate-account` | Pública (nuevo)             | Crear/confirmar contraseña y estados finales del enlace                                                  |
| `/login`            | Pública                     | Aviso: activar la cuenta desde el correo antes de iniciar sesión                                         |

Componentes (`src/invitations/`): `types.ts`, `service.ts` (`invitations`, `accounts`), `queries.ts`, `format.ts`, `components.tsx` (`StatusBadge`, `InvitationsPanel`, `InviteProviderAdminDialog`, `InviteDriverDialog`, `InviteButton`), `pages.tsx` (`InvitationsPage`); `src/auth/ActivateAccount.tsx`. Compartidos: `publicApi` en `services/api.ts` y `Table.emptyTitle`.

Estados mostrados (sólo los del contrato):

- Cuenta: `INVITED` → Invitación pendiente, `ACTIVE` → Activo, `DISABLED` → Deshabilitado.
- Invitación: `PENDING` → Invitación pendiente, `EXPIRED` → Expirada (derivado por el backend), `ACCEPTED` → Aceptada, `REVOKED` → Revocada.

Reenviar y revocar sólo aparecen en `PENDING` y `EXPIRED`, ambos con confirmación. Reenviar advierte que el enlace anterior deja de funcionar. Si `emailDelivery` es `FAILED`, la invitación queda registrada y la UI pide reenviarla.

## Aislamiento de PROVIDER_ADMIN

- Sólo ve Repartidores/Vehículos/Mi proveedor; no ve Administradores ni Invitaciones y `/users`, `/invitations` muestran 403 sin llamar a la API.
- Sólo puede invitar DRIVER. El proveedor sale del selector existente basado en sus propias memberships (`/provider/profiles`); `providerId` viaja sólo como query para el `ProviderMembershipGuard`, que es la autoridad. Validado: listar o invitar en otro proveedor responde 403 y enviar `role` en el body responde 400.
- [Invitar repartidor] se deshabilita cuando la capacidad del proveedor está completa; el backend además cuenta invitaciones pendientes (`PROVIDER_DRIVER_LIMIT_REACHED`).
- DRIVER no tiene UI administrativa de usuarios; puede activar su cuenta e iniciar sesión (dashboard sin módulos).

## Activación

- El token se lee una vez de `?token=`, se guarda sólo en memoria del componente y se retira de la barra y del historial (`navigate(..., { replace: true })`). Nunca se muestra ni se persiste. Se envía únicamente en el body de `POST /auth/activate-account` mediante `publicApi`: sin `Authorization`, sin refresh de sesión aunque haya una abierta.
- `index.html` declara `<meta name="referrer" content="no-referrer">` además del header de Nginx.
- Política real: 16–128 caracteres (`PASSWORD_MIN_LENGTH`/`MAX` del backend); se valida longitud y coincidencia antes de llamar a la API.
- Éxito: "Cuenta activada correctamente." y botón a Login. No hay login automático (el backend no devuelve sesión).
- Estados finales (ocultan el formulario): `INVITATION_TOKEN_INVALID` o enlace sin token → "La invitación no es válida."; `INVITATION_EXPIRED` → "Esta invitación ha expirado. Solicita una nueva invitación a tu administrador."; `INVITATION_ALREADY_ACCEPTED` → "Esta invitación ya fue utilizada."; `INVITATION_REVOKED` → "Esta invitación ya no está disponible."; `ACCOUNT_NOT_ACTIVATABLE` y `PROVIDER_DRIVER_LIMIT_REACHED` con mensajes seguros. 429, red y 500 conservan el formulario para reintentar.
- Login de una cuenta pendiente o deshabilitada: el backend responde el mismo `401 Invalid credentials` que una contraseña incorrecta (no revela el estado), así que la web muestra el mensaje genérico y un aviso fijo para activar desde el correo.

## Errores

Los `code` del backend se traducen en `services/errors.ts`: `USER_ALREADY_ACTIVE`, `USER_INVITATION_PENDING`, `USER_DISABLED`, `PROVIDER_DRIVER_LIMIT_REACHED` (409), `INVITATION_NOT_PENDING` (409), `INVITATION_RESEND_COOLDOWN` (429), `MAIL_NOT_CONFIGURED` (503) y los de activación. El mensaje genérico de 429 pasa a "Demasiados intentos. Intenta nuevamente más tarde." en toda la web. Nunca se refleja texto crudo del backend.

## Hallazgos

1. **Bug corregido (preexistente desde V1.3):** `ActionForm` con `initialDirty` (login, diálogos de confirmación, activación) registraba el aviso `beforeunload` de "cambios sin guardar" sin que la persona hubiera editado nada. Salir de la página de login hacía que Chromium bloqueara el aviso y lo registrara como error de consola, lo que rompía la fase final de `test:e2e:provider-admin`; en la activación, recargar habría mostrado un aviso falso. Ahora `initialDirty` sólo habilita el envío y el aviso requiere ediciones reales. Cubierto por un test de regresión.
2. El panel de invitaciones agregaba un segundo botón "Buscar" en Repartidores, ambiguo para lectores de pantalla (lo detectó un test V1.4). Ahora se anuncia "Buscar invitaciones".
3. El login no distingue cuentas pendientes (decisión del backend para no revelar estados); documentado arriba.
4. **Bug corregido en la verificación final (V1.6):** el detalle de cotización mostraba `DELIVERY_REQUEST_CANCELLED` crudo como motivo; ahora se traduce con `cancellationReasonLabel`.
5. `docs/API-CONTRACT.md` tenía la sección V1.6.1 sin formato Prettier; se formateó sin cambiar contenido.
